# Interface languages: English, Arabic and Urdu

One design system, three interface languages. English is the reviewed source; **the Arabic and Urdu interface strings
are drafts that need review by a qualified translator**, and the footer says so (`draftArabicUi`, `draftUrduUi`).

## Routing

| URL | Language |
| --- | --- |
| `/ar/...` | Arabic, always (sets the `qitl-locale` cookie to `ar`) |
| `/ur/...` | Urdu, always (sets the cookie to `ur`) |
| `/en/...` | chooses English: sets the cookie to `en`, then a 307 to the unprefixed URL |
| any other path | the cookie's language (`en`, `ar` or `ur`), English when missing or unknown |

The middleware (`src/middleware.ts`) rewrites unprefixed paths to `/en|ar|ur/...` internally, so every link in the app
stays a plain path and every variant is statically generated (`generateStaticParams` uses `LOCALES`). It imports only
`src/lib/i18n/locales.ts` (no dictionaries). The sitemap and the layout's `alternates` list all three.

The language switch (`LangToggle`, `src/components/shell/toggles.tsx`) is three plain links, EN / العربية / اردو, each at
least 44x44px, in the reading and journey headers (from 480px up) and in the Explore sheet (phones). It works without
JavaScript because the links go through `/en`, `/ar` and `/ur`. Switching keeps the page and the query; with JavaScript it
also keeps the `#hash` (`langHref`; a fragment never reaches the server, and browsers keep it across the `/en` redirect).

## Strings

- Shell strings: `src/lib/i18n/dict.ts` (`getDict(locale)` gives `{ locale, dir, t }`). Arabic and Urdu must have every
  English key (unit test `tests/unit/i18n.test.ts`).
- **Module strings: `src/lib/i18n/modules/`.** A module adds its own file instead of editing `dict.ts`:

  ```ts
  // src/lib/i18n/modules/dreams.ts
  import { moduleStrings } from "./index";
  export const dreamStrings = (locale: string) =>
    moduleStrings(locale, {
      en: { title: "Dream Understanding", ask: "Request interpretation" },
      ar: { title: "فهم الرؤى" },          // partial is fine: missing keys fall back to English
      ur: { title: "خوابوں کی سمجھ" },
    });
  ```

  English is required and defines the shape; Arabic and Urdu are optional and may be partial, at any depth. Unknown
  keys and values of the wrong type are ignored. Example: `modules/reader.ts`.
- **Every strings file is listed in `src/lib/i18n/registry.ts`.** `tests/unit/i18n-coverage.test.ts` fails when an
  Arabic or Urdu string is missing (a leaf equal to its English, unless it is a name, a code or one of the few leaves
  kept English on purpose); `scripts/i18n-inventory.ts --write` regenerates `docs/LOCALISATION_STATUS.md` (coverage per
  module and every hard-coded English string with file:line).
- Shared strings: `modules/ui.ts` (shell, footer, breadcrumbs, error pages, evidence labels, cards, drawers, timelines,
  map legends); each area has its own file (`home`, `prophets`, `story`, `events`, `atlas`, `hadith`, `reader`,
  `search`, `community`, `account`, `admin`, `api`, and the module files).
- Getting the language: server components use their `params.locale`; client components call `useLocale()`
  (`src/lib/i18n/useLocale.ts`, the `[locale]` route segment). The design-system components in `src/components/ui`
  (`EvidenceLabel`, `EditorialStatus`, `DraftBadge`, `EraTag`, `HadithGrade`, the cards, `MapLegend`, `SearchField`)
  are client components that follow the page's language by themselves.
- API errors: routes keep their English `error` and a stable `code`; client components show `apiErrorText(locale,
  body)` (`modules/api.ts`), the message for the code in the interface language.
- **English content in an Arabic or Urdu page** (database rows, the journey, editorial pages, names) is marked with
  `{...englishContent(locale)}` (`lang="en" dir="ltr"`), so punctuation sits on the right side and screen readers switch
  voice. Editorial pages show a short note that their text is English.
- Interface sentences that state a religious fact are not translated by the site: the Nuh note (Life Through the Ages),
  the first sentence of the Last Hour lead and its Q 7:187 note, and the qira'at distinction points stay English
  (marked `lang="en"`) until a qualified translator and the scholarly reviewers supply them.
- Drafting: Lara may produce a first pass; a person corrects it, and religious terms come from `translation_glossary`.
  Honorifics stay as in CLAUDE.md: ﷺ and (عليه السلام), in Arabic script inside Urdu too.

## Typography

- Urdu interface text is **Noto Nastaliq Urdu** (`src/app/fonts.ts`, `--ff-nastaliq`, not preloaded). Under
  `html[lang="ur"]` the `--font-sans` and `--font-display` stacks put Nastaliq after the Latin face, so Latin keeps Plex /
  Source Serif and Arabic-script text gets Nastaliq (`src/styles/i18n.css`).
- Nastaliq needs a line height of about 2: the body and every interface control set with a fixed px line height
  (buttons, pills, navigation, labels, the bottom bar) get `line-height: 2` in Urdu. `tests/e2e/urdu.spec.ts` checks at
  320px that no Urdu control has a line height under 1.8x its font size or clips its content.
- No letter spacing and no case transforms on Arabic-script interfaces (`html[lang=ar|ur] *`, except `[lang=en]` blocks).
- Arabic inside the Urdu interface (`lang="ar"` blocks) keeps its Naskh / Plex Arabic stacks; **Quranic Arabic always uses
  `--font-quran`** (Amiri Quran), never Nastaliq.

## Three language preferences

Independent settings (docs/proposals/2026-10-31-briefs-review.md section 1), logic in `src/lib/i18n/prefs.ts`, hook
`useLanguagePrefs()` in `src/lib/i18n/useLanguagePrefs.ts`:

| Preference | Signed out | Signed in (also) |
| --- | --- | --- |
| Interface language (`en`, `ar`, `ur`) | `qitl-locale` cookie | `profiles.locale` |
| Quran translation language (`en`, `ur`, `none` = Arabic only) | localStorage `qitl-lang-prefs` | `story_playback_preferences.quran_translation_language` |
| Narration language (`en`, `ar`, `ur`) | localStorage `qitl-lang-prefs` | `story_playback_preferences.language` |

Defaults follow the interface language (Urdu: Urdu translation and narration; Arabic: the Arabic alone). Migration
`20261031001900_language_preferences.sql` adds the translation column and limits the narration column; both rows are
private to their reader (RLS). The interface language is in `profiles` (publicly readable) because the column already
existed there; nothing else personal is stored with it.

UI: the full panel (`LanguagePrefsPanel`) on `/account` (kept on the device when accounts are not available), and a
compact one that opens in place from the language note in the Quran reader and the Story view (`LanguageNote`). A
preference never makes text appear: a translation or narration is shown only from a licensed, reviewed edition
(`pickAvailable`), otherwise the note says it is unavailable.

## Tests

- `tests/unit/i18n.test.ts`: locale resolution and fallback, dictionaries, `moduleStrings`, preferences.
- `tests/unit/middleware.test.ts`: `/ur`, the cookie, `/en`, unknown values.
- `tests/db/production.test.ts`: the preference columns' checks and privacy.
- `tests/e2e/urdu.spec.ts`: switch, fonts, no clipping at 320px, preferences, axe at 360px and 1440px.
- `tests/e2e/responsive.spec.ts`: the full sweep runs for `en`, `ar` and `ur` (routes in `tests/e2e/routes.ts`).
- `tests/unit/i18n-coverage.test.ts`: every registered strings file has Arabic and Urdu; `englishContent`,
  `apiErrorText`, `langHref`.
- `tests/e2e/i18n.spec.ts`: every route in `/ar` and `/ur` renders no English interface words (a heuristic word list)
  outside `lang="en"` content; switching language keeps the page, query and hash; English content is marked.

## Not done yet

- Page bodies (prophet chapters, methodology, legal pages) are English text; in the Arabic and Urdu interfaces they are
  shown as they are, marked `lang="en" dir="ltr"`. Translating them is content work for a qualified translator.
- The large editorial forms (`src/components/admin/*`: tools, interpretation, creation, story, qira'at, life-through-ages,
  guidance and licences editors, the studio) are still English inside a localised admin shell; see
  docs/LOCALISATION_STATUS.md for the list.
- The interface language saved on the profile is not applied automatically on sign-in on another device (the cookie wins).
